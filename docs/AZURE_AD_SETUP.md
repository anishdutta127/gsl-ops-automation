# Azure AD setup for GSL Ops Automation - guide for Mafatlal IT

This document covers the Microsoft Entra ID (Azure AD) app registration we need so GSL/Mafatlal staff can sign in to the GSL Ops Automation platform with their existing work account. Anish owns the integration on the GSL side and is the contact for any questions.

## What we need from you

After the app registration is complete, please return:

1. **Tenant ID** - the directory (tenant) ID for the Mafatlal Azure AD instance.
2. **Client ID** - the application (client) ID from the app registration. (Already received: `791b9974-a130-4840-82fd-48730010a9a0`.)

That is the full list. **No client secret is needed** - the app uses public-client / PKCE flow, which authenticates the browser to Microsoft without a long-lived shared secret. PKCE is the Microsoft-recommended pattern for SPA + web app sign-in.

You do **not** need to provide a JWT signing secret or any session-encryption key. Those are generated by us internally (using `openssl rand -hex 32`) and are separate from the Azure AD integration.

## App registration settings

| Field | Value |
|---|---|
| Display name | `GSL Ops Automation` |
| Supported account types | **Accounts in this organizational directory only** (single tenant) |
| Platform | Web |
| Redirect URI (production) | `https://gsl-ops-automation.vercel.app/api/auth/callback/microsoft-entra-id` |
| Logout URL | not required |
| Front-channel logout URL | not required |
| Implicit grant / hybrid flows | both checkboxes left unticked |
| Allow public client flows | **Yes** (this is the key change vs the secret-based pattern; enables PKCE) |
| Token endpoint authentication method | **none** (public client) |

The single-tenant setting constrains sign-in to the Mafatlal directory so personal Microsoft accounts (live.com / outlook.com) and other tenants are blocked at the Microsoft endpoint, never reaching our code.

External stakeholders who are not in the Mafatlal directory can still sign in **only if** Anish has pre-created their user record in GSL Ops. See "Pre-approved external stakeholders" below.

## API permissions

Grant the following Microsoft Graph **delegated** permissions:

| Permission | Type | Reason |
|---|---|---|
| `openid` | Delegated | Required for OIDC sign-in. |
| `profile` | Delegated | Read the user's display name (rendered as the homepage greeting). |
| `email` | Delegated | Read the user's email address (used to match against an existing GSL user record OR create a new pending record for admin review). |
| `User.Read` | Delegated | Read the user's profile (specifically the `oid` claim - the immutable Azure AD object ID that we store as the stable foreign key). |

No application permissions needed. No admin consent for any tenant-wide scopes.

## What we store on our side, where

| Value | Where | Encrypted? |
|---|---|---|
| Tenant ID | Vercel env var `AUTH_MICROSOFT_ENTRA_ID_TENANT_ID` | Yes (Vercel's KMS) |
| Client ID | Vercel env var `AUTH_MICROSOFT_ENTRA_ID_ID` | Yes |
| Optional email-domain allowlist | Vercel env var `AUTH_MICROSOFT_ENTRA_ID_ALLOWED_DOMAINS` | Yes (defence-in-depth; comma-separated `getsetlearn.info,mafatlal.com`) |
| Self-generated session secret | Vercel env var `AUTH_SECRET` | Yes (generated by us with `openssl rand -hex 32`; not from you) |

Source code references the env vars; values are never committed to the repo.

## Pre-approved external stakeholders

GSL Ops occasionally needs to let stakeholders OUTSIDE the Mafatlal Azure AD tenant sign in (auditors, partners, advisors). For these users:

1. Anish creates a user record in `src/data/users.json` with their email, role, and department BEFORE they attempt to sign in.
2. The user signs in with their own Microsoft account (any tenant; personal accounts still blocked).
3. Our app checks: "is this email in users.json?" If yes, link the Microsoft identity to that record and let them through with the role + permissions Anish set.
4. If the email is not in users.json and not in the corporate allowlist (`AUTH_MICROSOFT_ENTRA_ID_ALLOWED_DOMAINS`), we reject with: "Account not authorised. Contact your GSL administrator for access."

Mafatlal IT does not need to invite these users as guests in the Mafatlal directory. The pre-approved-email check happens entirely on our side.

## What changes at production migration

The repo is currently hosted on Vercel at `https://gsl-ops-automation.vercel.app`. When GSL moves to a permanent production domain (e.g. `ops.getsetlearn.info`), we will request that you:

1. Add a **second** Redirect URI to the same app registration:
   `https://ops.getsetlearn.info/api/auth/callback/microsoft-entra-id`
2. Leave the existing Vercel URL in place during the migration window.
3. Once the new domain is verified, you can remove the Vercel URI if desired.

No new app registration is required for the production migration. The same Tenant ID + Client ID continue to work.

## Optional hardening (defer if unclear)

- **Conditional Access** policies (require MFA, block legacy auth) can be applied at the tenant level; we do not enforce them on our side. If you want to require MFA for everyone signing in to GSL Ops, configure it in the Mafatlal CA dashboard.
- **Authentication policy** to disable password-based sign-in for users who have an Azure AD account is a directory-level decision, not ours. Worth a separate conversation if Mafatlal IT wants to retire username/password fully.

## How sign-in works for a user

1. User visits `https://gsl-ops-automation.vercel.app/login`.
2. Clicks "Continue with Microsoft" (the button is disabled with a tooltip until the env vars are set).
3. Browser performs the PKCE handshake with Microsoft (generates a code verifier, sends a code challenge, gets back an authorization code).
4. Microsoft authenticates them against the Mafatlal directory (with MFA if your CA policy requires it).
5. Microsoft redirects back to our callback URL with the authorization code.
6. Our app exchanges the code + the PKCE verifier for an ID token + userinfo, then:
   - Looks up our user record by email.
   - If found, signs them in (existing role + permissions preserved).
   - If not found AND the email is on the corporate allowlist, creates a pending user record (no access until Anish promotes them).
   - If not found AND outside the allowlist, rejects with "Account not authorised. Contact your GSL administrator for access."
7. User lands on the homepage with their existing GSL role + department, or on the rejection notice.
